# 为其他项目配置经济型子 agent

目标是在满足项目质量要求的前提下，减少重复阅读、重复审查和无效委派。主 agent 的模型与推理强度始终由用户选择。

这是一套待实测的配置基线，不是已测得的最优方案。当前壁纸项目只验证了配置语法和加载，没有测量成本、漏检率或返工率。

## 先认识项目，再决定角色

配置前读取项目贡献指南、构建入口、领域术语和相关架构决策；定向检查代表性模块和已有测试，避免先扫描整个仓库。

确认以下信息，无法从仓库确认的内容明确列为未知：

| 要识别的内容 | 配置时如何使用 |
| --- | --- |
| 技术栈、模块边界、调用方式 | 确定探索范围和审查需要追踪的调用链 |
| 常见改动及其影响 | 区分主 agent 自查、普通审查和高风险审查 |
| 项目真实风险 | 将高风险审查条件写成具体行为，而非“重要改动” |
| 可用构建、测试和手动验证步骤 | 由主 agent 集中执行，避免子 agent 重复验证 |
| 已有配置、技能和模型权限 | 合并现有规则；核对冲突和客户端支持，保留用户设置 |

项目风险举例：

| 项目类型 | 可选的高风险触发条件 |
| --- | --- |
| Windows 桌面应用 | 文件删除、进程通信、并发、播放生命周期、多显示器状态切换 |
| Web / API 服务 | 身份认证、权限边界、跨租户访问、数据库迁移、支付与幂等 |
| 前端应用 | 登录状态、敏感信息展示、支付流程、关键交互的可访问性 |
| 数据任务 | 覆盖或删除数据、Schema 变化、重复处理、断点恢复 |
| SDK / 公共库 | 公共接口、序列化协议、兼容性、线程安全 |

只选与当前项目有关的风险，并替换成仓库已有术语。跨文件或跨项目本身不自动等于高风险。

## 最小配置基线

| 角色 | 启用条件 | 本次选用的模型基线 |
| --- | --- | --- |
| 主 agent | 始终负责实现、整合和最终验证 | 用户自由选择 |
| explorer | 入口、调用链或影响范围不明确 | gpt-6-luna / high |
| reviewer | 范围明确、值得独立复核的一般逻辑变更 | gpt-6-luna / high |
| risk_reviewer | 命中项目具体高风险条件 | gpt-6.1-sol / medium |

角色按需存在：小型项目可以先只配置 reviewer，有真实需求再补其他角色。定义三个角色不代表每个任务都启动三个 agent。

以下模型名称是 2026-10-30 核对官方文档时采用的选择。复用时重新核对官方推荐、账号可用模型和客户端支持；模型不支持时明确说明并选择可用替代，不能静默退回未知默认值。

项目 `.codex/config.toml` 的基线：

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 2
default_subagent_model = "gpt-6-luna"
default_subagent_reasoning_effort = "high"
```

并发上限不包含主 agent。项目配置不新增顶层 `model` 或 `model_reasoning_effort`，避免限制主 agent 的选择；已有设置先核实用途再处理。

在 `.codex/agents/<name>.toml` 定义实际需要的角色，每个文件包含 `name`、`description`、`model`、`model_reasoning_effort` 和 `developer_instructions`。模型与推理强度成对指定。description 写清触发条件，developer_instructions 写清范围和完成标准。

审查角色的最小交付约定：只读指定变更及相关调用链，返回有证据的缺陷、严重程度、位置、触发条件和影响；无发现时明确说明，并列出未验证项。探索角色返回入口、调用方、相关文件与符号、风险和未知项。

只读约定是行为指令，不是权限隔离；子 agent 继承父会话权限。

## 节省来自执行规则

- 文案、简单样式、位置已知的低风险小改动由主 agent 自查。
- 高风险任务直接交给 risk_reviewer；不固定执行“普通审查后再完整高级审查”。普通审查发现超出范围的问题时，传递已有证据，仅补查未解决风险。
- 主 agent 统一写文件、构建和验收。默认子 agent 只读且不递归委派；用户或适用技能明确要求的流程按其要求执行。
- 子 agent 接收目标、必要路径、约束和交付格式。支持独立上下文时只传必要信息；确实依赖聊天历史时保留所需上下文。
- 独立任务才并行；存在依赖时先收齐前置结果。主 agent 在子 agent 工作期间处理其他事项，避免重复探索同一范围。
- 子 agent 返回简短证据摘要；主 agent 对关键结论定向核验，避免将原始文件和日志重新塞回主线程。
- 验证范围匹配变更风险；检查通过后，仅在新变更、失败或未解决疑点出现时追加验证。
- 将调度规则简短写入 AGENTS.md，模型配置放 TOML，长指南按需读取，避免每轮加载重复说明。

## 验证与调整

1. 检查 TOML 语法、必填字段、角色名称和调度规则一致性，确认未固定主 agent。
2. 用本机支持的配置诊断工具检查加载；语法通过不能证明字段生效，CLI 加载成功也不能替代桌面端实际验证。
3. 在新会话中，用一个低风险任务和一个项目真实高风险任务验证角色与模型选择。
4. 对代表性任务比较单 agent 与委派方案的最终正确性、返工、总耗时和可获得的总用量；计入所有子 agent、重试和后续修复。缺失用量不能视为零。
5. 出现漏检或返工时，先缩小任务范围、补充证据或调整触发条件，再决定是否升级模型；不要仅凭单次 token 更低判断方案更好。

API token 费用和订阅额度是不同口径，不能直接用 API 单价推算订阅消耗。

## 可直接交给其他项目的提示词

```text
请为当前项目配置经济型 Codex 子 agent，先读取仓库贡献指南、构建入口、相关架构文档和现有 agent 配置，定向了解技术栈、模块边界、测试方式及真实风险。

要求：
1. 保留主 agent 的模型与推理强度自由选择，只配置子 agent。
2. 按需选择 explorer、reviewer、risk_reviewer；小项目减少角色。核对当前官方文档和账号可用模型，轻量任务选低成本模型，高风险任务选能力更强的模型。可参考 Luna/high 与 Sol/medium，但不要机械照搬或使用不支持的字段。
3. 并发子 agent 上限从 2 开始。小改动主 agent 自查；普通逻辑按需独立审查；高风险任务直接使用高级审查，避免完整重复审查。
4. 按当前项目具体风险制定触发条件，沿用项目术语。主 agent 统一修改与验收，子 agent 默认只读、不递归委派，仅返回证据摘要。
5. 合并现有配置与技能规则，保留无关设置和用户改动。AGENTS.md 只补简短调度规则，不引入与项目无关的角色、工具或流程。
6. 验证语法和客户端加载，说明实际验证范围。汇报修改文件、项目适配理由和未验证项，不宣称未经实测的节省比例。

请直接完成配置；只有仓库证据不足且影响方案的关键问题才询问我。
```

## 官方依据与项目选择

[OpenAI Subagents 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)说明模型与推理配置、子 agent 的上下文隔离、用量开销和权限继承。[部署指南](https://developers.openai.com/api/docs/guides/deployment-checklist)建议比较单 agent 与多 agent 的质量、延迟和成本。

“最多两个子 agent、主 agent 统一写入、普通与高风险审查分流”是本次项目采用的经验基线，不是官方统一要求。
