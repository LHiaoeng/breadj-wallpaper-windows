## 1. 本次验证范围

在后端实际 Maven 依赖上运行隔离测试，没有启动完整业务应用，没有连接 MySQL、Redis 或修改现有 OAuth 客户端和用户。

测试采用实际 SAS Provider、实际 OAuth2 客户端认证过滤器与 Token 端点过滤器、内存授权存储。Ballcat 用户查询服务使用 Mockito 替代持久层，实际 UserDetailsService 完成 CUSTOMER 主体转换。测试不是替代认证逻辑的模拟实现。

端点验证通过 Spring Mock 请求/响应运行真实 Servlet 过滤器，不是经 TCP 连接的部署接口联调。默认授权规则的测试也不是整个生产安全链的覆盖证明。

实际依赖：Ballcat 1.4.2、Spring Boot 2.7.12、Spring Security 5.7.8、SAS 0.4.2。Maven 使用 Java 8，编译 380 个主源码文件和 46 个测试源码文件。

## 3. 实测结果

| 测试 | 观测 | 能证明什么 |
| --- | --- | --- |
| Token 端点公共客户端 + PKCE | 返回 HTTP 200、Bearer access_token，无 refresh_token | 现有协议过滤器可完成公共客户端换码，但缺少续期凭据 |
| Token 端点错误 verifier | HTTP 400、invalid_grant，无访问令牌 | 错误 PKCE 不会成功换码 |
| Provider 公共客户端换码 | 有访问令牌、无刷新令牌 | 缺少刷新令牌是 SAS Provider 行为，不是桌面解析遗漏 |
| 错误/缺失 verifier（两项） | 拒绝认证 | PKCE 验证可复用 |
| 授权码重放 | 第二次换码 invalid_grant | 授权码一次性能力可复用 |
| 换码 redirect 不一致 | 拒绝换码 | 已签发授权码的回调绑定有效；不代表动态端口注册验证通过 |
| 已认证机密客户端对照组 | 获得 30 天 refresh token，刷新后 token 值及原到期时间不变 | 既有刷新能力可复用，但固定窗口不是自动滚动续期；对照组不证明客户端 secret 认证本身 |
| 用户记录禁用后刷新 | 已读取的 CUSTOMER 快照仍可生成新访问令牌 | 仅改数据库状态，不会让默认刷新 Provider 自动重查用户状态 |
| authenticated-only 规则 | 无角色 CUSTOMER 也满足“已登录” | 已登录不等于管理员，必须增加类型/权限边界 |
| 撤销 refresh token | 对应 access/refresh 均不活跃，后续刷新失败 | SAS 具备单条授权撤销原语，可用于退出/重置适配 |

**11 项通过代表观测结论可复现，不代表原样接入满足产品验收。**

## 4. 不能直接上线的缺口

### 4.1 公共桌面客户端的 30 天续期

SAS 0.4.2 的 `OAuth2AuthorizationCodeAuthenticationProvider` 在客户端认证方式为 NONE 时不签发刷新令牌。`PublicClientAuthenticationProvider` 使用授权码的 PKCE 校验，不能简单当作通用无密钥刷新认证。

因此，注册一个公共客户端并把 refresh TTL 改为 30 天不足以完成接入；只替换 Token 生成器同样不能解决全部问题。

带共享密钥的旧 `breadj_client_web` 示例不能直接搬进 Windows。把客户端改标为机密客户端、内置同一个 secret 虽然可能让示例换码成功，但不是合格解决方案。访问令牌也不应直接延长为 30 天。

最小适配方向：保留现有 SAS 和 CUSTOMER，单独验证桌面公共客户端的安全续期扩展，覆盖签发、刷新时客户端/用户绑定、轮换与重放处理、冻结/重置撤销。若需要最小会话扩展或字段，应仅围绕这些不变量增加，不改建账号平台。单纯升级版本不作为默认解法，因为现行 SAS 指南也明确列出了公共客户端刷新限制。

在该扩展通过隔离测试之前，不应先把 Windows 登录 UI 当成已可交付功能。本次没有编写未经验证的生产认证扩展，也没有选用“每半小时打开浏览器”降低已确认体验。

### 4.2 CUSTOMER 与管理端的隔离

实际 Ballcat UserDetailsService 能读取 CUSTOMER 并保留 type、userId，这是可复用能力；但默认“已登录”授权没有管理员类型检查。无角色只会阻止有相应权限校验的操作，不能保证所有后台接口均被隔离。

需要在资源授权边界覆盖管理路由，检查 SYSTEM 身份及现有权限；客户端私有路由则检查 CUSTOMER 和本人归属。还要对登录入口限制账号类型，防止管理员登录状态被普通用户流程混用。公开壁纸与必要回调仍按最小路径放行。

本次没有改动完整安全链；必须在独立应用上下文中验证真实路由的 401/403、公开接口兼容、CUSTOMER 与 SYSTEM 交叉访问，再接入现有应用。

### 4.3 临时密码、重置和冻结

静态核查：现有 `User.isCredentialsNonExpired()` 恒为 true，不能直接作为“首次必须改密”的实现。`SysUserServiceImpl.updatePassword` 当前执行密码哈希及数据库更新，未见自动撤销 OAuth 授权的调用；未在应用源码发现相应撤销监听。

实测也证明刷新默认使用保存的身份快照。因此需要：

1. 一个可持久化的最小强制改密状态，优先复用已有可用字段，确无则补字段；不是只在客户端显示弹窗。
2. 服务端在改密前拒绝私有业务，只放行必要账号状态、改密和退出。
3. 管理员重置/冻结与授权撤销协调；明确并发刷新不能在撤销后生成一个新的可用会话。
4. 使用者改密完成后撤销临时授权，再进入正常会话；临时密码不写日志，管理员不能查询真实密码。

单条撤销原语已验证。跨设备授权枚举、浏览器会话清理、缓存失效和并发重置尚未实测，不能把单条撤销测试扩大为“退出全部设备已完成”。

## 5. 最小实施顺序

只围绕账号 M0 补齐以下三项，不并行扩大到收藏 UI 或签到积分：

1. 在隔离安全配置中验证 CUSTOMER/SYSTEM 的完整路由边界，使用实际权限组件检查公开接口兼容。
2. 验证公共客户端的续期扩展及撤销一致性。先解决已确认的 30 天要求，再落地桌面登录；不引入另一个身份库。
3. 验证临时改密状态和重置流程，再做 Windows 系统浏览器、loopback 回调、DPAPI 持久化及重启恢复联调。

账号首版按正式运营规划，由管理员开通账号，暂不提供自行注册或找回，不建独立 `client_member`。如果续期方案确实需要调整部署形态或明显增加维护成本，应把具体技术结果带回决策，而非静默切换架构。
