## Question

依据账号边界调查，与用户确定可交接的 M0 路线：普通用户登录和管理员入口如何隔离；首次改密与撤销如何串联；系统浏览器退出、重启恢复与 loopback 端口采取哪种已验证策略；最小管理界面如何开通、交付独立临时密码、重置及冻结账号并记录审计。

沿用 PRD 的滚动登录目标及 CUSTOMER 身份：实际使用延长有效期，连续六个月无实际使用才过期。方案必须列明需要补齐的证据与部署条件，不能把现有固定 30 天候选通过测试等同 M0 通过。只定方案，不实施。

## Comments

前置证据：[核实账号安全候选与三端账号管理的真实接入边界](01-research-account-boundaries.md)。

### Grilling · 第一轮已确认（2026-10-30）

- 普通用户使用独立的系统浏览器登录入口，服务于 Windows 授权流程；不复用管理端登录页。
- 管理页面的第一轮选择已被下方最新决定替代。
- 临时密码交付当时尚未回答，后于第二轮确认。以上为过程记录，未形成整票决议。

### Grilling · 管理页面决定修订（2026-10-30）

- 新增独立的“普通用户管理”页面，面向正式运营。复用现有列表、分页等组件，账号继续保存在 `sys_user`，不新增客户表。
- 管理员通过专用后端接口开通、重置临时密码和冻结 CUSTOMER 账号；服务端固定 CUSTOMER 类型，并处理首次改密、审计及旧登录撤销。现有系统用户页继续承担 SYSTEM 账号操作。
- 此决定替代上方关于在现有系统用户页增加类型筛选的旧选择；其余问题随后进入第二轮。

### Grilling · 产品定位修订（2026-10-30）

- 首版按正式运营规划，账号由管理员开通，暂不提供自行注册；开通不以邀请资格为前提。

### Grilling · 第二轮已确认（2026-10-30）

- 开通或重置生成独立临时密码，仅向执行操作的管理员显示一次，由管理员通过指定安全渠道交付；不保存可再次查看的明文，不自动发送邮件或短信。具体渠道尚待定名。
- “普通用户管理”页面及 CUSTOMER 开通、重置、冻结接口使用专门的 SYSTEM 管理权限，界面可见性与后端授权分别检查。
- 首次改密在 Windows 客户端完成；服务端在改密前仅允许账号状态、改密及退出。改密成功撤销临时授权，再取得正常授权。
- Windows 退出撤销本机授权并清除本机凭据。再次登录须重新确认身份，系统浏览器仍有 Cookie 时也不能静默回到刚退出的账号；具体浏览器会话处理须经完整安全链验证。

### Grilling · 第三轮已确认及待定（2026-10-30）

- 临时密码由管理员核实接收人后，当面或通过已核验的一对一沟通渠道交付；没有可信渠道时暂缓交付。审计交付操作及接收人，不记录明文。
- 半年正常使用无需重复输密，替代原 30 天目标。此轮曾建议固定窗口，已被下方滚动有效期决定替代。
- 此轮曾建议预先注册的固定 `127.0.0.1` 回调端口，已被下方随机端口决定替代。
- “普通用户管理”页面包含解冻；解冻不恢复旧授权，用户重新登录。
- 审计开通、重置、冻结、解冻及结果，至少记录管理员、目标账号、时间和结果，复用现有审计能力，不记录临时密码明文。

### Grilling · 登录有效期与回调修订（2026-10-30）

- 正常使用时登录有效期滚动延长；连续六个月没有实际使用才过期。后台自动刷新本身不算活跃，不得因应用常驻而无限延期。退出、改密、重置、冻结或安全撤销仍可立即结束登录。哪些前台行为算实际使用及离线使用如何处理，留待下一轮定案。
- 正式运营以随机可用的 loopback 端口为目标，先验证现有授权服务对端口变化的支持，必要时做最小适配。固定端口仅是当前候选的已测配置，不作为最终回调策略。
- 现有续期候选按首次授权固定 30 天截止，不能只把 TTL 改为六个月；需要重新设计活跃依据、滚动期限、并发刷新/撤销及凭据重放后的失效测试。

### Grilling · 实际使用边界已确认（2026-10-30）

- 已登录用户在 Windows 前台主动浏览、搜索、收藏、下载、设置壁纸或操作账号，计为实际使用。仅播放桌面壁纸、应用常驻、自动刷新或后台请求不计。
- 离线操作可继续使用本地能力，但不延长服务端登录期限；重新联网后，仍有效的授权在下一次实际使用时延期，已过期的授权须重新登录。
- 每台设备的授权单独计算不活跃期限；设备 A 的使用不延长设备 B 的授权。
- 从服务端确认的最近一次实际使用时间起按六个日历月计算，不用固定 180 天代替。

### 候选代码核对（2026-10-30）

- 后端 `DesktopPublicClientAuthenticationProvider.validateClient` 把刷新 TTL 校验固定为 30 天；`DesktopTokenAuthenticationProvider` 在初次换码时写入固定 `desktop.refreshDeadline`，后续轮换沿用该截止时间。
- 已消费刷新凭据摘要在 `client_refresh_token_history` 按固定截止时间加访问令牌时长清理。滚动期限必须同时重审摘要保留、重放撤销、并发刷新与活动更新，不能只改注册客户端的 TTL。
- 当前测试仅使用精确注册的固定 loopback 回调。随机端口策略须在实际 SAS 版本与部署链验证。

### Resolution · 2026-10-30

用户确认下列整套方案为本票最终答案；候选可行性与部署证据按后续调查票验证。

## Answer

1. **账号与管理**：首版正式运营，暂不提供自行注册。复用 `sys_user` 的 CUSTOMER 身份；管理端新增独立“普通用户管理”页，复用现有列表、分页组件。SYSTEM 管理员凭专门权限调用固定 CUSTOMER 类型的开通、重置、冻结和解冻接口；现有 SYSTEM 用户管理流程保持原用。临时密码独立生成、仅向操作管理员显示一次；核实接收人后当面或经已核验的一对一渠道交付，无可信渠道时暂缓。审计操作人、目标账号、时间、结果及交付对象，不记录密码明文。
2. **登录与改密**：Windows 通过独立普通用户浏览器入口、授权码和 PKCE 登录，不混用管理端入口。随机可用 loopback 端口先监听后打开浏览器，校验 state、回调和一次性授权码；取消、超时及失败清理临时状态。首次改密在 Windows 完成，服务端此前只允许状态、改密和退出；成功后撤销临时授权并重新取得正常授权。
3. **登录期限与撤销**：各设备独立保存授权，Windows 使用 DPAPI CurrentUser。服务端确认已登录用户在前台主动浏览、搜索、收藏、下载、设置壁纸或操作账号后，将该设备期限滚动延至最近一次实际使用后的六个日历月。仅播放壁纸、后台刷新、应用常驻、后台请求及离线操作不延期；离线本地能力仍可用。退出清本机凭据和私有数据并撤销本机授权，再登录须重新确认身份；改密、重置、冻结及安全撤销使旧授权失效，解冻不恢复旧授权。重启恢复仍有效授权，过期后重新登录。
4. **实施前证据**：复用现有公共客户端安全续期候选，但其固定 30 天截止、客户端注册校验及已消费刷新凭据摘要保留逻辑都需适配滚动期限；后台刷新不得触发活动延期。验证活动更新与刷新/退出/重置/冻结并发、旧刷新凭据重放后整条授权失效，以及每设备独立期限。验证当前 SAS 版本、客户端注册及网关对随机 loopback 端口的支持；验证系统浏览器 Cookie 存在时退出后的重新认证、首次改密后的再授权和管理端权限。使用完整应用的真实 HTTP 安全链与隔离持久层，以及 Windows/目标部署联调；候选既有测试不等于 M0 通过。M0 验收前不推进 M1 交付。
